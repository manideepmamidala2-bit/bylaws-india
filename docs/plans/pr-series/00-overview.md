# Structured Building Bylaws — PR Plan Series: Overview

**Date:** 24 November 2026 · **Starting point:** commit `859fa77` and Audit 3 · **Replaces:** Plan v2.0

Read this file before any PR plan. Every PR plan (`01-…` to `11-…`) assumes the rules and definitions here.

---

## 1. Why this series exists

Audit 3 found that the engineering (pipeline integrity, reproducibility, schema, website, dg2n design) is real and good, but **all Bengaluru South data in release 1.0.0 was generated by a script in the repository**: 28 "source" PDFs, the wards, the zones and the corporation boundary. The release presented this as in-force law under the names of real authorities. That data is now replaced, step by step, with real data acquired from the web.

The cause was structural: one giant PR, no checkpoints, and acceptance checks that could be satisfied by data the agent produced. This series fixes that with small PRs, a provenance gate in CI, and three owner checkpoints.

---

## 2. Scope: building rules for Bengaluru South City Corporation

**Inclusion test** for any document or provision: *does it decide what can be built on a plot, or what a building must comply with to be approved and occupied?*

| Tier | What | Treatment |
|---|---|---|
| Core | Building Bye-laws 2003 and every amendment (including the 2026 South City Corporation amendment); RMP 2015 Zoning Regulations and every amendment; RMP 2015 land-use maps for Bengaluru South | Structured completely |
| Supporting | Building-relevant provisions of other instruments: fire NOC for buildings of 21 m and above; TDR rules as they affect usable FAR; occupancy certificate exemption orders; metro influence zone; lake buffers once their legal status is verified; anything else that passes the test | Only the relevant provisions structured; link to the full instrument |
| Register only | Whole Acts beyond their building provisions; procedural circulars; National Building Code (copyrighted by BIS) | Listed with links; not structured |

**English only.** A building instrument that exists only in Kannada is listed in the register with a declared gap.

## 3. Rules

All earlier rules still apply. Restated briefly:

- **R1** No jurisdiction-specific code; Bengaluru South lives only in config and data.
- **R2** Provenance on everything (source, page, position, version, retrieval record).
- **R3** Explicit legal status: `in_force`, `draft`, `superseded`, `withdrawn`, `status_unknown`.
- **R4** Licences: code Apache-2.0, data CC BY 4.0; dependency allowlist enforced in CI.
- **R6** Reproducible outputs; timestamps from `SOURCE_DATE_EPOCH`.
- **R7** Fail loudly. **R8** No defaults that strengthen a claim (no invented status, page, bounding box, version).
- **R9** Verified records never edited; new versions instead. **R10** Nothing `human_verified` unless a person verified it.
- **R11** Tests shown failing first; fixture expectations hand-written.
- **R12** Legal status and record version are separate.
- **R13** Copyrighted standards are references only.
- **R14** Anything derived by the project (consolidated text, traced zones, drawn buffers) is labelled derived, with method.

**New:**

- **R15 Provenance gate.** For any jurisdiction not marked `visibility: test`, every source file must have: an `http(s)` source URL; a retrieval record (timestamp, final URL after redirects, HTTP status, content type, content length, selected response headers); a SHA-256 of the fetched bytes; and an archive link (Wayback Machine snapshot) or a recorded reason it could not be made. CI fails on local or `file://` source URLs for public jurisdictions, and on any PDF whose metadata names a repository tool as creator or producer.
- **R16 Never generate source content.** The agent must never write, synthesise or reconstruct any document, map, boundary or figure presented as coming from an authority. If something cannot be obtained, it is declared as a gap and the work continues with what is real. Generated data exists only in test fixtures.
- **R17 Evidence quotes the source.** Status evidence, dates and notification numbers are quoted from the fetched document itself, never from a plan, a news article alone, or memory. News articles may be used to find documents, not as evidence of their content.
- **R18 Stop at checkpoints.** At each owner checkpoint the agent opens the PR, writes the checkpoint instructions in the PR description, and waits. It does not merge.

## 4. How documents are structured (summary; detail in PR 03)

1. **Faithful tree.** The native hierarchy exactly, down to the smallest citable unit. Addresses follow the Akoma Ntoso naming approach, built from ancestors (e.g. `bl_6.0__cl_i__item_2`). Lead-in text (`intro`) and closing text (`wrap_up`) stay with their parent. Every table row is its own item. Definitions record the term they define.
2. **Annotations beside the text, never inside it.** Stand-off notes pointing at exact character spans: cross-references, defined-term uses, provision types in this phase. Zone applicability only as needed for the map (PR 11). Quantities and full applicability are for the next phase.
3. **History.** Each item has dated versions. Amending instruments are stored as documents and as effects on their targets. A consolidated "as amended" view is derived and labelled.

## 6. Common definition of done for every PR

- CI green: tests, schema drift, licence allowlist, R1 check, provenance gate (from PR 02), accessibility (axe).
- `docs/progress.md` updated.
- PR description contains: preview URL, what changed, decisions made, known gaps, and checkpoint instructions where applicable.
- Nothing in production presents unverified or generated data as law.

## 7. Releases

- Release `1.0.0` (synthetic) is **withdrawn**: listed on the Data page as "Withdrawn: synthetic demonstration data, not the law of Bengaluru South", with no downloadable bundle.
- Real releases start at `2.0.0` (PR 05) and increase with each PR that publishes data. Release version comes from config, not a CLI default.
- Every release carries `declarations.json` stating coverage and gaps.
